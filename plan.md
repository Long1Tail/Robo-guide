# План перехода от LLM-болталки (`guide_robot_llm`) к VLM-оркестратору решений (`guide_robot_vlm`)

## 1. Введение и цели ТЗ

### 1.1. Контекст
В текущей архитектуре робота-экскурсовода за диалоговый контур отвечает пакет `guide_robot_llm` (`chat_node`). Он реализует простую голосовую «болталку»: получает распознанную реплику посетителя из `/asr/transcript`, обращается к текстовой LLM и озвучивает ответ через `Say.action` в `tts_node`.
При этом:
* Робот не использует визуальный контекст (робот «слышит», но не «видит»).
* Текстовая модель изолирована от управления поведением: она не может инициировать экскурсию, управлять остановками или реагировать на обстановку вокруг.
* Верхнеуровневые сценарии жестко зашиты в конечный автомат миссий (`guide_robot_mission_control`).

### 1.2. Цель
Реализовать мультимодальный модуль принятия решений на базе Vision-Language Model (**`guide_robot_vlm`**), который по триплету:
$$\text{(Кадр с камеры + Запрос посетителя + Состояние миссии)}$$
выбирает действие из фиксированной библиотеки навыков (**Tools**), формирует строго типизированные аргументы в формате JSON, валидирует их по семантической карте и исполняет через интерфейсы ROS 2.

### 1.3. Границы задачи (согласно ТЗ)
* **Входит:**
  * Добавление и подключение RGB-камеры (в Gazebo и на реальном железе);
  * Предобработка видеопотока (буферизация, ресайз, компрессия, Base64);
  * Развертывание и интеграция VLM (Ollama / vLLM с моделями класса Qwen2.5-VL / SmolVLM);
  * ROS 2 Lifecycle-узел `vlm_agent_node` с циклом Tool-Calling;
  * Двухуровневая валидация аргументов (`validator.py`);
  * Брокер исполнения навыков (`tool_broker.py`);
  * Реализация минимум двух новых мультимодальных навыков (разрешение дейксиса, оценка аудитории);
  * Набор данных для оценки качества и бенчмарк производительности на целевом железе.
* **Не входит:**
  * Низкоуровневое управление моторами и расчет траекторий (делегировано Nav2);
  * Изменение контура аппаратной безопасности (E-Stop, `collision_monitor` работают независимо);
  * Генерация произвольных текстов об экспонатах (все описания берутся по `content_id` из `guide_robot_semantic_map`).

## 2. Архитектура системы и топология взаимодействия

### 2.1. Топология информационных потоков

```
 ┌─────────────────────────┐
 │ /camera/color/image_raw │ (sensor_msgs/Image, QoS: SensorData, 15-30 Hz)
 └───────────┬─────────────┘
             │ [кольцевой буфер последнего кадра]
             ▼
 ┌─────────────────────────┐     ┌───────────────────────┐
 │   /asr/transcript       │     │    /mission/state     │
 │ (is_final=True, d10)    │     │ (MissionState, d1)    │
 └───────────┬─────────────┘     └───────────┬───────────┘
             │                               │
             ▼                               ▼
       ┌───────────────────────────────────────────┐
       │     vlm_agent_node (LifecycleNode)        │
       │                                           │
       │ 1. image_preprocessor (letterbox, JPEG)   │
       │ 2. vlm_backends (Ollama / vLLM / Mock)    │
       │ 3. validator (синтаксис + семантика)      │
       │ 4. history & turn_log (JSONL)             │
       └─────────────────────┬─────────────────────┘
                             │ ValidatedAction(tool, args)
                             ▼
       ┌───────────────────────────────────────────┐
       │                tool_broker                │
       └──────┬──────────────┬──────────────┬──────┘
              │              │              │
              ▼              ▼              ▼
       RunTour.action  Narrate.action  Say.action / Nav2
       (mission_fsm)   (narration_srv) (tts_node / nav2)
```

### 2.2. Интерфейсы ROS 2 пакета `guide_robot_vlm`

#### Входящие подписки:
1. `/camera/color/image_raw` (`sensor_msgs/msg/Image`, QoS `SensorData`) — постоянный прием кадров с камеры, сохранение последнего свежего кадра.
2. `/asr/transcript` (`guide_robot_msgs/msg/Transcript`, QoS `Reliable`, depth 10) — текстовая реплика посетителя от `guide_robot_voice`.
3. `/mission/state` (`guide_robot_msgs/msg/MissionState`, QoS `TransientLocal / Reliable`) — текущее состояние экскурсии (`stop_id`, `exhibit_id`, фаза FSM).
4. `/speech/cancel_all` (`guide_robot_msgs/msg/CancelAll`, QoS `Reliable`, depth 1) — аварийный обрыв речи и текущего рассуждения (Barge-in / стоп-слово).
5. `/voice/speaking` (`guide_robot_msgs/msg/SpeakingStatus`, QoS `TransientLocal`) — состояние динамика (для отсечения собственного голоса).

#### Исходящие публикации и клиенты:
1. `Say.action` (`guide_robot_msgs/action/Say`) — речевой ответ робота / уточняющий вопрос.
2. `RunTour.action` (`guide_robot_msgs/action/RunTour`) — запуск / отмена экскурсии в `mission_fsm`.
3. `Narrate.action` (`guide_robot_msgs/action/Narrate`) — запуск рассказа об экспонате по `content_id` в `narration_server`.
4. `NavigateToPose.action` (`nav2_msgs/action/NavigateToPose`) — навигация к экспонату или координатам.
5. `/mission_fsm/request_pause`, `/mission_fsm/request_resume` (`std_srvs/srv/Trigger`) — управление паузой экскурсии.
6. `/location_server/list_locations`, `/location_server/list_tours`, `/content_server/get_exhibit_content` — получение метаданных для валидации.
7. `/diagnostics` (`diagnostic_msgs/msg/DiagnosticArray`, 1 Гц) — телеметрия узла.
8. `/system_event` (`guide_robot_msgs/msg/SystemEvent`) — системные уведомления об ошибках бэкенда.

## 3. Подключение и обработка видеопотока с камеры

### 3.1. Виртуальная камера для Gazebo
В физической модели робота камера отсутствует. Для симуляции реализуются:
1. **URDF-описание (`guide_robot_description/urdf/guide_robot.urdf.xacro`):**
   * Создание `camera_link` на мачте робота на высоте 1.15 м от пола с наклоном вперед-вниз на 10° (`pitch = 0.174 рад`).
   * Создание `camera_optical_link` со смещением ориентации `rpy="-1.5708 0 -1.5708"` (ось Z смотрит в направлении оптической оси).
2. **Плагин Gazebo (`guide_robot_description/urdf/guide_robot.gazebo.xacro`):**
   * Подключение плагина `libgazebo_ros_camera.so`:
     * Разрешение: $640 \times 480$ пикселей;
     * Частота: 15–30 кадров/сек;
     * Горизонтальный угол обзора (HFov): 1.089 рад (~62°);
     * Формат: `R8G8B8`;
     * Публикация в топик `/camera/color/image_raw`.

### 3.2. Физическая USB-камера (на реальном роботе)
* Используется готовый пакет `v4l2_camera` (уже включен в Dockerfile образа).
* Создается launch-файл `camera.launch.py` с параметрами: `video_device: "/dev/video0"`, `image_size: [640, 480]`, `pixel_format: "YUYV"`.

### 3.3. Модуль предобработки `image_preprocessor.py`
Модуль представляет собой чистую Python-логику (без зависимостей от `rclpy`):
1. **Класс `ImagePreprocessor`:**
   * Принимает сырой буфер `bytes` и формат (`rgb8`, `bgr8`, `jpeg`).
   * Проверяет возраст кадра по таймстампу: отбрасывает кадры старше `max_frame_age_s` (дефолт 1.0 с).
   * Выполняет пропорциональное масштабирование (Letterbox resize): приводит изображение к квадрату $448 \times 448$ или целевому $640 \times 480$ с добавлением серых полей, сохраняя пропорции объектов.
   * Сжимает кадр в JPEG с качеством 80–85%.
   * Кодирует байты в Base64 Data URL: `data:image/jpeg;base64,...`.
2. **Структура данных `PreprocessedImage`:**
   * `b64_data: str`
   * `width: int`, `height: int`
   * `capture_timestamp: float`
   * `encoded_size_bytes: int`

## 4. Что переносится из `guide_robot_llm` в `guide_robot_vlm`

| Компонент `guide_robot_llm` | Статус переноса | Модификации в `guide_robot_vlm` |
|---|---|---|
| **Гейтинг ASR и активация** | Переносится | Добавляется логика: при наличии кадра формируется мультимодальный промпт; при отсутствии свежего кадра — переход в деградированный режим или отказ. |
| **Barge-in и `/speech/cancel_all`** | Переносится | Epoch-фенсинг хода: при получении прерывания немедленно выставляется `abort_event`, останавливающий генерацию VLM. |
| **Echo Guard** | Переносится | Игнорирование ASR-транскрипта, пока робот воспроизводит собственную реплику через TTS. |
| **Клиент `Say.action`** | Переносится | Используется для озвучки реплик робота и сообщений об ошибках (`SCOPE_DIALOG`, `PRIORITY_DIALOG`). |
| **`lib/history.py`** | Модифицируется | Запись ходов дополняется выбранным инструментом (`tool`), аргументами (`args`) и визуальной сводкой. |
| **`lib/turn_log.py`** | Модифицируется | Запись в JSONL обогащается полями: `tool`, `args`, `confidence`, `abstain`, `frame_timestamp`, `latency_ms`. |
| **`lib/sentence_splitter.py`** | Переносится | Применяется, если VLM генерирует развернутый текст описания сцены. |
| **`lib/qos.py`** | Переносится | Используются готовые единые профили QoS для аудио- и системных сообщений. |

## 5. Библиотека навыков (Tools) и формат вывода VLM

### 5.1. Формат вывода модели (Фаза 1 ТЗ)
Модель отвечает **СТРОГО в формате JSON** без свободного текста.

```json
{
  "tool": "describe_exhibit",
  "args": {
    "content_id": "hall_1_stand_c1"
  },
  "confidence": 0.94,
  "abstain": false
}
```

* `tool` *(string, обязательное)*: имя навыка из закрытого списка.
* `args` *(object, обязательное)*: словарь аргументов конкретного навыка.
* `confidence` *(float, 0.0 .. 1.0)*: самооценка уверенности модели.
* `abstain` *(bool)*: флаг осознанного отказа от выбора действия (при шуме, неясности).

### 5.2. Базовый набор инструментов

1. **`start_tour(tour_id)`**:
   * Назначение: старт экскурсионного маршрута.
   * Вызов: `RunTour.action` в `mission_fsm`.
2. **`stop_tour()`**:
   * Назначение: досрочная остановка экскурсии.
   * Вызов: `cancel_goal` активного `RunTour`.
3. **`goto_exhibit(location_id)`**:
   * Назначение: навигация к выбранному стенду/локации.
   * Вызов: `NavigateToPose.action` в Nav2.
4. **`describe_exhibit(content_id)`**:
   * Назначение: включение кураторского рассказа об экспонате.
   * Вызов: `Narrate.action` в `narration_server`. Текст берется из базы семантической карты, модель **не генерирует** текст от себя.
5. **`ask_visitor(question_text)`**:
   * Назначение: задание уточняющего вопроса человеку.
   * Вызов: `Say.action` в `tts_node`.
6. **`wait()`**:
   * Назначение: временная пауза (например, посетители отстали).
   * Вызов: сервис `~/request_pause` в `mission_fsm`.
7. **`idle()`**:
   * Назначение: перевод в безопасное состояние ожидания.
   * Вызов: завершение хода без управляющих воздействий на физические компоненты.

### 5.3. Новые VLM-навыки (мультимодальные)

#### Навык 1: Разрешение дейксиса (Deixis Resolution)
* **Пользовательский сценарий:** Посетитель указывает рукой на один из экспонатов и спрашивает: *«А что это за штука?»* или *«Расскажи про вот это»*.
* **Работа VLM:** На вход модели подаются кадр камеры, текущая локация робота и список видимых в этой зоне экспонатов. Модель по направлению жеста определяет конкретный объект и сопоставляет его с допустимым списком.
* **Результат:** Модель возвращает `tool: "describe_exhibit"`, `args: {"content_id": "stand_radar_c1"}`. Робот начинает рассказ о выбранном объекте.

#### Навык 2: Оценка аудитории (Audience Assessment)
* **Пользовательский сценарий:** Робот остановился у экспоната или ведет рассказ. Необходимо понимать, слушают ли его люди.
* **Работа VLM:** Модель оценивает количество людей перед роботом и их вовлеченность (направлены ли лица к роботу).
* **Результат:** Если посетители отвернулись или отошли — модель возвращает `tool: "wait"`, ставя рассказ на паузу. Когда внимание возвращается — подается сигнал возобновления (`~/request_resume`).

#### Навык 3: Описание сцены по запросу (Scene Description)
* **Пользовательский сценарий:** Посетитель спрашивает: *«Что ты сейчас видишь?»*
* **Работа VLM:** Модель формирует краткое описание кадра (люди, обстановка), но любые упоминания экспонатов сверяются с белым списком `guide_robot_semantic_map`. Текст озвучивается через `Say.action`.

#### Навык 4: Визуальная проверка обстановки (Visual Clearance)
* **Пользовательский сценарий:** Робот собирается начать движение, но перед ним вплотную встал человек.
* **Работа VLM:** Обнаружение визуальной блокировки прохода как дополнительный контекст к лидарам.
* **Результат:** Вызов `ask_visitor` с вежливой просьбой освободить проход.

## 6. Двухуровневый семантический валидатор (`validator.py`)

Для исключения сбоев и галлюцинаций выход модели проходит строгую проверку до передачи в исполнитель:

```
[Вывод VLM] ──► [Уровень 1: Синтаксис и флаги]
                      │
                      ├── Невалидный JSON / Неизвестный tool / abstain=True / confidence < 0.7
                      │   └──► [БЕЗОПАСНЫЙ ФОЛБЭК: idle + переспрос через Say]
                      │
                      ▼
                [Уровень 2: Семантическая проверка аргументов]
                      │
                      ├── location_id нет в ListLocations?
                      ├── content_id нет в GetExhibitContent?
                      ├── tour_id нет в ListTours?
                      │   └──► [ОТКЛОНЕНИЕ: idle + сообщение об ошибке]
                      │
                      ▼
                ValidatedAction ──► [Передача в ToolBroker]
```

**Инвариант безопасности:** Ни при каких обстоятельствах непроверенные или некорректные идентификаторы не попадают в исполнительные клиенты.

## 7. Брокер исполнения навыков (`tool_broker.py`)

Класс `ToolBroker` транслирует `ValidatedAction` в асинхронные вызовы Action/Service клиентов ROS 2:
* `execute_start_tour(tour_id)` $\to$ отправка цели в `ActionClient[RunTour]`.
* `execute_stop_tour()` $\to$ отправка запроса отмены активного goal.
* `execute_goto_exhibit(location_id)` $\to$ получение координат из `semantic_map` и отправка в `ActionClient[NavigateToPose]`.
* `execute_describe_exhibit(content_id)` $\to$ отправка цели в `ActionClient[Narrate]`.
* `execute_wait()` $\to$ вызов сервиса `request_pause`.
* `execute_idle()` $\to$ завершение хода.

## 9. План тестирования, бенчмаркинга и оценки качества

### 9.1. Уровни тестирования
1. **Юнит-тесты (`pytest guide_robot_vlm/test`):**
   * Быстрые тесты без ROS 2 и звуковых карт.
   * Покрытие: предобработка изображений, парсер и валидатор схем, логирование и история.
2. **Интеграционные тесты узла:**
   * Проверка жизненного цикла (`on_configure` $\to$ `on_activate` $\to$ `on_deactivate`).
   * Проверка реакции на ASR-сообщение в связке с Mock VLM и фиксация отправки цели в Mock ToolBroker.
   * Проверка аварийного прерывания по `/speech/cancel_all`.

### 9.2. Датасет валидации навыков (Evaluation Dataset)
Формируется набор из 50+ эталонных сценариев в формате JSON:
* Вход: тестовое изображение (или синтетический рендер) + текст пользователя + состояние миссии.
* Ожидаемый результат: эталонный JSON (`tool`, `args`, `confidence`).
* Категории тестов:
  * Базовые голосовые команды (*«Начнем тур»*, *«Стой»*);
  * Дейксис с указанием на разные экспонаты (*«Что это?»*);
  * Оценка аудитории (кадр с людьми, смотрящими на робота / кадр с ушедшими людьми);
  * Негативные тесты и шум (*«Какая погода на Марсе?»* $\to$ `idle` / `abstain: true`);
  * Попытка взлома/галлюцинации (*«Поехали к неизвестному стенду 999»* $\to$ отлов валидатором).

### 9.3. Бенчмарк на целевом железе
Замер характеристик на видеокарте NVIDIA с локальным бэкендом (Ollama / vLLM):
* **Time To First Token (TTFT) / Latency:** время от получения кадра и реплики до генерации JSON-действия (целевое: $\le 1.5$–$2.0$ сек на GPU);
* **Action Accuracy:** процент корректно выбранных инструментов на датасете (целевое: $\ge 90\%$);
* **Argument Validity:** процент валидных `content_id` / `location_id` (целевое: $100\%$ благодаря валидатору);
* **VRAM Footprint:** потребление видеопамяти при одновременной работе VLM и ROS 2 узлов.
